1. MAKE update_state THE SINGLE AGING OPERATION

Current implementation:
- evaluate_age owns the backward-Euler/exact aging formulas and speed derivative.
- update_state(speed, old_state, dt) validates the mature positive-rate convention, then returns evaluate_age(...constant_rate_exact).age.
- update_state(fractions, speed, old_state, dt) only checks a vector size and calls the other overload.
- Signed trial resistance and bulk-tip accepted-history preparation bypass update_state and call evaluate_age.
- The mature surface caller constructs compositions and fractions solely for the unused mixture argument.

Replace this chain with ONE canonical update_state operation that directly contains the existing common aging implementation. A suitable interface is:

  struct StateUpdate
  {
    double age;                  // theta at the requested duration, seconds
    double derivative_wrt_speed; // d theta / d nonnegative slip speed
  };

  StateUpdate update_state(double slip_speed,
                           double old_state,
                           double duration,
                           AgingMethod method) const;

Retain the existing explicit AgingMethod enum. All maintained callers must select the method explicitly. Returning a value and derivative together is justified by their common computation and the Newton chain rule; this small result record is not a new history owner.

Remove evaluate_age and the old forwarding update_state overloads after migrating callers. Do not leave compatibility aliases, another same-purpose helper, a second age evaluator, or a new state-update class. The function is const and computes a candidate; it does not commit history. Explain this in its documentation.

Preserve:
- theta_dot = 1 - speed*theta/Dc with the existing global Dc;
- both backward-Euler and constant-rate exact updates;
- zero-speed aging, zero-duration identity, stable expm1 evaluation, the small-argument derivative and subnormal-speed limit;
- immutable incoming age for every Newton and line-search trial;
- nonnegative speed as input: signed callers pass abs(V), with the correct signed chain rule handled in resistance evaluation;
- stateful-law rejection and finite/positive input checks.

The common mathematical update accepts zero speed. Preserve the mature positive-rate/Vmin restriction at its actual mature caller or existing owning validation boundary, rather than imposing it on the common zero-speed-capable aging law. Do not silently clamp rates. Document the unified API's input domain and retain checks on mature production paths. This is an interface consolidation, not permission to change the mature constitutive convention.

Keep each time location unchanged:
- mature surface history and its timestep-state predictor: exact update over the requested full duration;
- bulk-tip BE trial and publication: BE over full dt;
- midpoint resistance trial: exact constant-stage-rate aging from the accepted old age over dt/2;
- midpoint endpoint publication: exact aging from the SAME accepted old age over full dt, using the accepted integrated section rate.
Do not substitute the root-resolved rate for the independently integrated rate used by accepted section history.

Remove the mixture-taking aging overload: fractions do not enter the current global-Dc equation. In compute_surface_state_candidates, remove the composition gathering and fraction construction performed solely for this call. Retain composition data and mixture evaluation where they actually affect friction or other material properties. Do not add future heterogeneous-Dc machinery.

2. NAME THE THREE DISTINCT RESISTANCE OPERATIONS BY WHAT THEY DO

Use this interface mapping, updating result records, all consumers, comments, and active documentation together:

  signed_endpoint   -> evaluate_resistance
  section_endpoint  -> solve_section_slip_rate
  section_primitive -> compute_resistance_potential
  SignedEndpoint    -> ResistanceResponse
  SectionEndpoint   -> SectionSlipSolution

Their responsibilities remain distinct:
- evaluate_resistance evaluates signed friction plus radiation resistance at a supplied signed rate, after the selected trial aging update. Return resistance, total derivative with respect to signed slip rate, trial age, and separate friction/radiation contributions.
- solve_section_slip_rate solves V + mobility*f(V) = free_rate. Return the solved rate, its evaluated resistance response, and the derivative df/d(free_rate) required by the condensed coupling.
- compute_resistance_potential evaluates the integral from 0 to V of f(v) dv, holding incoming history and other parameters fixed. It is used for nonlinear search; it is NOT stored energy or physical dissipation f(V)*V.

Use explicit member names for different derivatives. Avoid the current law.law nesting and ambiguous derivative/force_derivative naming in the changed caller code. For example, resistance_response, slip_rate, derivative_wrt_slip_rate, and resistance_derivative_wrt_free_rate make the meanings visible. Avoid renaming unrelated physical history fields merely to match these temporary result names.

These are different mathematical operations, not duplicate algorithms to inline into one large function. Retain their separation. Also retain genuine shared private computations, such as effective RSF parameters and the coefficient with fixed-state partial derivatives. The target is fewer redundant interfaces and clearer responsibilities, not a minimum function count.

Preserve the existing root bracket, asinh coordinate, monotonicity guard, convergence criterion, iteration budget, signed/zero-rate behavior, and Gauss48 search quadrature. Do not change physical quadrature or friction laws during this cleanup. The default old names and endpoint labels should disappear from maintained code after migration. Historical archived evidence may retain its original names.
