## Make the code readable at the point of use

- Apply the existing `AGENTS.md` baseline and use the nearest upstream example. Keep short signatures on one line. When a signature wraps, use one named parameter per line in declarations and definitions, aligning names where it helps. At call sites with long argument lists, make the correspondence easy to read. Show input, output and in/out semantics, especially when an optional output preserves a caller-supplied value. Split long `declare_entry` calls so the pattern and description can be read easily. Preserve the resolved help text, including significant spaces in adjacent C++ string literals.
- Give private operations and local variables names a new reader can interpret from the caller. Expand packed declarations, several actions on one line, deeply nested expressions and opaque conditionals where they hide the calculation. Keep conventional symbols in a short equation when that makes the physics easier to recognize. Define the symbols where they enter. Write comments about purpose, units, sign, frame, time level and ownership wherever those distinctions affect interpretation. Prefer one clear definition in the owning header over repeating it at every use.
- Keep the numerical operation visible. Use a local name or a small private helper where it exposes an existing coherent step. Preserve public and protected source interfaces used by plugins, data layout and serialization order. Keep module ownership, file organization, solver strategies, allocations and communication patterns intact. Preserve evaluation order, accumulation order, branching at ties, exception conditions and MPI collective order. Algebraic rewrites can change a selected fault angle even when they look equivalent on paper. Record independently discovered design or correctness issues separately. A readability pass gives no authority to change their behavior.
- Apply the same care to verification code. A maintainer should be able to tell what is being measured, in what units, which value is the reference, which identity or clock is compared, and why a negative control is expected to fail. Preserve checker exit status, diagnostics relied upon by callers, thresholds, CLI and output schemas.
